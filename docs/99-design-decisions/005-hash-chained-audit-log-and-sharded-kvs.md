# ADR-005: Hash-Chained Audit Ledger & Sharded KVS Persistence

## Status
Accepted (Hardened with Monotonic Head Locking, Staged Sharding, HMAC Part 11 Seals & Honest Platform Boundaries)

## Context
Medical device quality systems subject to 21 CFR Part 11 and IEC 62304 require tamper-evident audit trails attributing every record mutation (live ingestion, Confluence spec drift, issue binding, test evidence recording, and electronic sign-off) to a verified actor and timestamp. Storing an unbounded audit array inside a single KVS compliance document would risk silent truncation, race conditions under concurrent updates, and exceeding Forge KVS item limits. At the same time, documentation must state honestly what software hash chaining in Atlassian Forge KVS does—and does not—provide compared to hardware WORM storage or X.509/PKI infrastructure.

## Decision
1. **Tamper-Evident Hash-Chained Ledger ([src/audit-log.ts](../../src/audit-log.ts)):**
   - Persist a chain head pointer (`{ lastSeq, headHash }`) at `medtrace:audit:head` and individual entries at `medtrace:audit:entry:<seq>` (bounded by `MAX_AUDIT_ENTRY_BYTES = 220 * 1024` bytes).
   - Chain each entry from `AUDIT_GENESIS_HASH` (`'0'.repeat(64)`) using `computeAuditEntryHash` (canonical sorted-key JSON SHA-256 via [src/crypto-utils.ts](../../src/crypto-utils.ts) over exact fields: `seq`, `timestamp`, `actorAccountId`, `action`, `targetKey`, `details`, `prevHash`, `authMethod`).
   - Write each entry with `kvs.set(..., { keyPolicy: 'FAIL_IF_EXISTS' })` and monotonic `setHead` updates (`returnValue: 'PREVIOUS'`), plus forward tail resolution (`resolveChainTail` scanning in 10-entry probes up to 500 hops across up to 12 concurrency retries).
   - Support cursor pagination via `getAuditLog(limit, beforeSeq?)` and bounded incremental window verification (`verifyAuditChain({ fromSeq, maxEntries, expectedPrevHash })`, capped by `MEDTRACE_AUDIT_VERIFY_MAX_ENTRIES` = `500` default / `200` in Custom UI resolver, anchored against verified predecessor `fromSeq - 1`), reading entries in `AUDIT_BATCH_CHUNK_SIZE = 25` KVS `batchGet` chunks and stepped sequentially by frontend modals via [auditVerify.ts](../../static/frontend/src/auditVerify.ts). `getEntriesBatch` filters `failedKeys` with `error.code === 'KEY_NOT_FOUND'` as not-present (expected for unseeded tail probes) and retries only non-`KEY_NOT_FOUND` codes once before failing closed.
2. **Sharded Compliance Suite & Save-Before-Audit Rollback ([src/seeder.ts](../../src/seeder.ts)):**
   - Persist suite metadata (`medtrace:compliance:suite_meta`, `ShardedSuiteMetaV2`, `SHARDED_V2`, bounded by `MAX_KVS_META_BYTES = 128 * 1024`) separately from individual trace links (`medtrace:compliance:link:<id>`), storing an `issueKeyIndex` (`work.key` / `hazard.key` -> link keys, sharded into `medtrace:compliance:meta_index:v<version>:<idx>` via `issueKeyIndexShardKeys` when root metadata would exceed `128 KiB`) for O(1)/bounded issue-scoped release-gate lookups (`getActiveComplianceSuite({ issueKeyFilter })`).
   - Protect concurrent mutations via optimistic `vlock` (`VLOCK_PREFIX`) versioning: commit `<= 25` operations within `MAX_TRANSACT_BYTES` atomically using `kvs.transact()`, and commit `> 25` operations using delta shard reuse for unchanged `v<version>:` link payloads alongside staged new/modified link keys, meta shard indices, `batchSetStrict`/`batchGetStrict` fail-closed retries, and stale shard garbage collection.
   - Wrap mutations in `commitSuiteMutation` with save-before-audit ordering and compensating rollback if audit append fails.
   - Isolate Forge runtime vs local Node test adapters via `isForgeRuntime()` ([src/runtime.ts](../../src/runtime.ts)).
3. **21 CFR Part 11 Hybrid ECDSA P-256 + HMAC Seals & Resumable Live Ingestion ([src/compliance-engine.ts](../../src/compliance-engine.ts), [src/ingestion.ts](../../src/ingestion.ts)):**
   - Electronic sign-off requires `passwordConfirmed: true`, exact `attestationPhrase === PART11_ATTESTATION_PHRASE`, Forge session identity verification (`UserIdentityResolver`), and either `HMAC-SHA256-SEAL-V1` (`MEDTRACE_PART11_SECRET`, with non-destructive key rotation verification via `MEDTRACE_PART11_PREVIOUS_SECRETS`) or hybrid asymmetric `ECDSA-P256-SHA256+HMAC-SEAL-V1` (verifying client ECDSA P-256 `prime256v1` signatures over `computePart11ClientChallenge` alongside bound server HMAC seals so a server-only secret holder cannot forge an asymmetric sign-off), persisted as composite `(hazardKey, specId)` `SignedSpecBaseline` records (`SIGNED_SPEC_PREFIX`).
   - `LiveIngestionService` short-circuits Jira `/issue` and AGG GraphQL fetches for untagged non-safety issues lacking Confluence links (`requireConfluenceLinkToEnrich: true`), persists and consumes resumable `nextPageToken` pagination cursors (`medtrace:ingestion:cursor:<projectKey || 'GLOBAL'>`) across truncated multi-invocation syncs, preserves existing trace links across other Jira projects or unreached issues after sync truncation, enforces revert non-resurrection when Confluence pages revert to hashes older than an invalidation timestamp, and runs `handleConfluencePageUpdated` with `MAX_CAS_RETRY_ATTEMPTS = 3`.
4. **Honest Immutability & Compliance Scope:**
   - SHA-256 hash chaining + `FAIL_IF_EXISTS` in Forge KVS + `HMAC-SHA256-SEAL-V1` provide **software tamper-evidence** within the Atlassian Cloud tenant; optional `ECDSA-P256-SHA256+HMAC-SEAL-V1` adds client private-key signature verification (user-managed/WebCrypto ECDSA P-256 keys, verified server-side alongside HMAC).
   - **Platform Limitation:** Atlassian Forge KVS (`@forge/kvs`) is **not** hardware WORM media, does **not** use an app-controlled HSM, and does **not** run a managed X.509 certificate authority (CA) unless external PKI issuance is paired with client keys. Tenant/Atlassian platform administrators or apps executing in the same Forge storage context could overwrite storage keys (which `verifyAuditChain()` subsequently detects as broken hashes or gaps). Export dossiers and verified audit trails ([FdaExportModal.tsx](../../static/frontend/src/components/FdaExportModal.tsx) / [AuditLogModal.tsx](../../static/frontend/src/components/AuditLogModal.tsx)) to controlled QMS archive storage if hardware WORM archival is required.

## Consequences
- Concurrent compliance mutations cannot silently drop audit entries or clobber suite shards, and post-hoc KVS edits break `verifyAuditChain()`.
- Separate link and metadata sharding scales beyond single-key Forge KVS limits while preserving clean rollback guarantees.
- Documentation, security posture ([SECURITY.md](../../SECURITY.md)), and sync governance ([docs/00-how-to/sync-docs-runbook.md](../00-how-to/sync-docs-runbook.md)) remain transparent about Forge KVS tamper-evidence vs hardware WORM/HSM/PKI.
